## Поддерживаемость политик

Нужно определить поведение FIC для политик, которые невозможно применить на конкретной ОС или в конкретной конфигурации системы.

Возможный вариант — добавить в модель политики отдельный признак:

```text
policy_supported
```

или аналогичный механизм, позволяющий различать:

- политика поддерживается;
- политика не поддерживается;
- применимость политики невозможно определить;
- политика потенциально поддерживается, но отсутствуют необходимые компоненты системы.

Возможно, одного `bool` здесь будет недостаточно.

## `SYSCTL_rp_filter_enable`

Необходимо пересмотреть поведение политики `SYSCTL_rp_filter_enable`.

Сейчас политика устанавливает:

```text
net.ipv4.conf.all.rp_filter
net.ipv4.conf.default.rp_filter
```

При этом NetworkManager может отдельно задавать значения для конкретных интерфейсов, например:

```text
net.ipv4.conf.enp5s0.rp_filter = 2
net.ipv4.conf.wlan0.rp_filter = 2
```

В результате настройки отдельных интерфейсов потенциально могут отличаться от значений, заданных политикой FIC.

### Возможные варианты

1. Удалять или комментировать настройки `rp_filter` для отдельных интерфейсов.
2. Явно переопределять их значениями, требуемыми политикой FIC.
3. Учитывать конфигурацию NetworkManager и связанные с ней механизмы при применении политики.

Требуется определить наиболее корректное поведение.

### Зависимости и рекомендации между политиками

Более общий вариант решения — добавить модель взаимосвязей между политиками.

Например:

- **зависит от** — политика не может корректно работать без другой политики;
- **рекомендуется** — совместное применение другой политики желательно, но не обязательно;
- **конфликтует с** — политики не должны применяться одновременно.

Например, для политики:

> Включение IPv4 `rp_filter`

может быть рекомендована политика:

> Отключить MPTCP в NetworkManager

Такой политики пока нет.

Возможная конфигурация NetworkManager:

```ini
[connection.no-mptcp]
connection.mptcp-flags=0x1
```

## PAM

Необходимо протестировать поведение PAM при наличии:

- бессмысленных правил;
- противоречащих друг другу правил;
- правил, позволяющих обойти применяемые FIC защитные настройки;
- модулей, завершающих обработку PAM-стека раньше защитных модулей.

Например:

```pam
auth sufficient pam_allow.so
```

Такое правило может разрешить аутентификацию и завершить обработку соответствующей части PAM-стека до выполнения последующих проверок.

При этом ниже могут находиться защитные настройки FIC:

```pam
auth requisite pam_faillock.so preauth silent audit deny=5 unlock_time=300
```

Нужно проверить реальные варианты обхода политик и определить, должен ли FIC:

- обнаруживать такие правила;
- предупреждать администратора;
- считать политику неприменённой;
- перестраивать PAM-стек;
- запрещать применение конфигурации с известным обходом.

## Удобство администрирования в GUI

Некоторые политики требуют в качестве значения готовый JSON. Это не удобно. Вероятное решение:
- Меняем TextEdit на кастомный TextEditWindow
- TextEditWindow при нажатии открывает НОВОЕ окно, специально созданное для задания значения именно этой политики (например, вместо того, чтобы писать готовый JSON администратор будет делать это в специальном окне внешне напоминающем утилиту GUFW).


## Известные ошибки

Скрипт удаление для Альта (preun) удаляет pam-topology через control, обходя rollback-механизм FIC. Для Debian/Ubuntu есть похожая проблема.

Текущая архитектура DC-правила не позволяет создать rollback-механизм. Требуется переработка. Нужно перевести их на модель с выбором значений new/all. Тогда rollback будет заключаться в простом переобходе бд устройств
