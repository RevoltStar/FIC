# FIC 2.0: руководство для агентов

Этот файл — короткая карта репозитория и набор обязательных правил. Не заменяй
им документацию компонентов. Перед началом новой задачи прочитай:

1. `docs/HANDOFF.md` — текущее состояние работы и незавершенные задачи.
2. `README.md` — краткую карту компонентов.
3. Только относящиеся к задаче README и разделы
   `docs/architecture-diagrams.md`.

## Статус версий и миграции

- У проекта пока нет стабильных или поддерживаемых релизов. До отдельного
  объявления стабильной версии обратная совместимость между изменениями кода
  не является требованием.
- При изменении форматов конфигурации, схем баз данных, daemon API, runtime
  paths и других внутренних или внешних контрактов не добавляй миграции,
  compatibility aliases, dual-read/dual-write и fallback на старый формат,
  если это прямо не требуется текущей задачей.
- Предпочитай чистую замену старого формата новым и синхронно обновляй все
  актуальные producers/consumers, seed-данные, конфиги по умолчанию, install и
  packaging rules, тесты и документацию.
- После объявления стабильной версии это правило должно быть пересмотрено:
  требования совместимости и миграции определяются отдельно для каждого
  поддерживаемого релиза.

## Архитектурные границы

- `fic/` — привилегированный системный демон и единственный владелец изменения
  конфигурации политик и их применения к ОС.
- `fic-cli/` и `fic-gui/` — клиенты daemon API. Они не должны напрямую писать
  в `/opt/fic/config` или самостоятельно применять политики.
- `fic-session-agent/` — непривилегированный агент графической сессии. Он
  сообщает демону метаданные своей сессии, но не получает значения политик и
  не применяет их.
- `fic-dick/` — сборщик и актуализатор базы устройств. Он работает с
  `/opt/fic/db/devices.db` через `fic-common/fic-device-db`.
- `fic-common/fic-ipc/` — публичная граница Unix socket/JSON IPC.
- `fic-common/fic-core/` — общие низкоуровневые утилиты: конфиги, файлы, логи,
  запуск процессов, блокировки и проверка хэшей команд.
- `fic-common/fic-device-db/` — общий слой SQLite для демона и `fic-dick`.
- `fic-common/fic-policy/` — базовая модель политики, результата применения и
  типов значений. Конкретные политики остаются в `fic/src/modules/`.

Не копируй реализацию общей функциональности обратно в компоненты и не
подключай внутренние заголовки одного исполняемого компонента из другого.

## Куда идти с задачей

- Маршрутизация daemon API и ответы IPC:
  `fic/src/main.cpp`.
- Compile-time профили дистрибутивов и runtime-проверка `/etc/os-release`:
  `fic/src/platform/` и `cmake/FicTargetPlatform.cmake`.
- Инициализация `PolicyMap`, применение, enable/disable/set:
  `fic/src/core/main_function.cpp` и `main_function.h`.
- Конкретная политика:
  `fic/src/modules/<module>/...`, соответствующий файл
  `fic/src/scripts/config/<MODULE>.conf` и локализация
  `fic/src/scripts/lang/{ru,en}.lang`.
- IPC-клиент, формат базового ответа и `FIC_SOCKET_PATH`:
  `fic-common/fic-ipc/include/fic/ipc/FicIpcClient.h`.
- Работа с конфигурациями, файлами, логами и процессами:
  `fic-common/fic-core/`.
- Схема и операции базы устройств:
  `fic-common/fic-device-db/include/fic/device-db/DB.h` и `src/DB.cpp`.
- Сбор устройств:
  `fic-dick/src/core/` и `fic-dick/src/modules/`.
- GUI политик и отправка изменений:
  `fic-gui/src/mainwindow.cpp`.
- Дерево устройств:
  `fic-gui/src/DeviceTree.*` и `DeviceAttributeList.*`.
- Просмотр логов:
  `fic-gui/src/LogService.*`, `LogModel.*`, `LogViewer.*`.
- Графические сессии:
  `fic/src/session/`, `fic-session-agent/` и `docs/session-agent.md`.
- Системные файлы, systemd, udev, локализация и seed-данные:
  `fic/src/scripts/`.
- Пакеты:
  `packaging/deb/` и `packaging/rpm/`. При изменении общей логики упаковки
  проверь все поддерживаемые Debian-скрипты и ALT p11, а не только один файл.

## Инварианты безопасности и поведения

- Доступ к `/run/fic/fic.sock` определяется правами Unix-сокета. Группа `fic`
  означает полный административный доступ ко всему daemon API. Не ослабляй
  владельца, группу, режимы `0770`/`0660` или проверку default runtime path без
  явного требования.
- Дерево `/opt/fic` принадлежит `root:fic`, но группа имеет только чтение и
  traversal/execute: каталоги `2750`, обычные файлы `0640`, исполняемые файлы в
  `/opt/fic/bin` — `0750`. Не возвращай group-write на конфиги, БД, hash store,
  lock-файлы, notification spool или бинарники; административные изменения
  выполняются через сокеты.
- Административный IPC использует одно `AF_UNIX/SOCK_SEQPACKET`-соединение на
  запрос: один JSON-пакет до `64 KiB`, затем фреймированный JSON-ответ общим
  размером до `1 MiB`. Первый пакет должен прийти за 2 секунды, запись ответа
  завершиться за 5 секунд; одновременно принимается не более 32 клиентов.
  Ответы должны сохранять единый минимум `{"ok": bool, "message": string}`.
- После изменения значения или состояния политики демон должен перечитать
  `PolicyMap`.
- GUI и CLI обязаны показывать текст ошибки демона, а не заменять его общим
  сообщением.
- Изменения файлов конфигурации должны сохранять существующую атомарную модель
  записи через временный файл, `fsync` и `rename`.
- Перед добавлением прямого запуска системной утилиты изучи существующие
  `ProcessExecutor` и `VerifiedProcessExecutor`. Для привилегированных
  фиксированных команд предпочитай проверяемый путь, если только сценарий
  пользовательской сессии не требует иной модели.
- Не выполняй реальные policy apply, lock/unlock, device mutation, udev trigger,
  установку пакетов или запись в `/opt/fic` как обычную проверку: это меняет
  состояние хоста. Такие проверки требуют явного запроса пользователя и
  подходящего тестового окружения.

## Сборка и проверка

Проект использует CMake и C++17. Полная локальная проверка:

```bash
cmake -S . -B build-check -DFIC_TARGET_PLATFORM=<target>
cmake --build build-check -j2
```

Поддерживаемые значения `<target>`: `debian-12`, `debian-13`,
`ubuntu-24.04`, `alt-p11`. Профиль обязателен и должен соответствовать целевой
ОС, а не ОС build-хоста.

Для узкой задачи можно собирать цель:

```bash
cmake --build build-check --target fic
cmake --build build-check --target fic-session-agent
cmake --build build-check --target fic-cli
cmake --build build-check --target fic-dick
cmake --build build-check --target fic-gui
```

Можно собирать компонент отдельно, как описано в его README. Полная конфигурация
требует SQLite3, OpenSSL, Threads, nlohmann/json и Qt Widgets (Qt 5 или Qt 6).

В проекте есть отдельные CTest-цели для общих путей, SSH, sudoers, sysctl и
профилей платформ. Минимум для изменения — успешная сборка затронутых целей и
относящиеся к ним тесты; для общих библиотек, IPC, CMake или
packaging-sensitive кода — полная сборка. Runtime-проверки описывай отдельно и
не выдавай их за выполненные, если они не запускались.

Пакеты собираются отдельными скриптами:

```bash
./packaging/deb/build-fic-debian12-deb-docker.sh <version>
./packaging/deb/build-fic-debian13-deb-docker.sh <version>
./packaging/deb/build-fic-ubuntu2404-deb-docker.sh <version>
./packaging/rpm/build-fic-alt-p11-rpm-docker.sh <version>
```

Они тяжелые, используют Docker и создают артефакты в `dist/`; не запускай их
без необходимости.

## Правила изменения проекта

- Сначала проверь `git status` и не перезаписывай пользовательские изменения.
- Делай минимальные изменения в зоне задачи; не смешивай рефакторинг с
  исправлением поведения.
- При изменении daemon API синхронно проверь CLI, GUI, IPC-документацию и
  `docs/architecture-diagrams.md`.
- При добавлении или переименовании политики проверь регистрацию в
  `init_policyMap()`, конфиг модуля, обе локализации и клиентское отображение.
- При изменении runtime-файлов проверь и CMake install rules, и ручную staging-
  логику deb/rpm-скриптов.
- Не редактируй содержимое `build*/` и `dist/` как исходники.
- Обновляй README или архитектурную документацию, если поменялись публичные
  команды, ответственность компонента, runtime paths либо формат IPC.
