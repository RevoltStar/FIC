границы компонентов находятся в `AGENTS.md`.

## Сделано

- В корень репозитория добавлен `SECURITY.md`, который GitHub распознает как
  security policy.
- Единственным каналом для деталей уязвимости указан GitHub Private
  Vulnerability Reporting; личная электронная почта не публикуется.
- Политика честно фиксирует отсутствие стабильных и security-supported релизов:
  отчеты по `main` принимаются без compatibility или remediation SLA.
- Определены scope для привилегированного демона, IPC, Unix-группы `fic`,
  trusted-command цепочки, package lifecycle, политик, устройств, миграций и
  поставляемых сторонних компонентов.
- Out-of-scope формулировка ссылается на актуальный список target platforms в
  `README.md` и не исключает платформонезависимую уязвимость только потому, что
  ее впервые обнаружили на другой ОС.
- Заданы целевые сроки ответа, coordinated disclosure, правила тестирования и
  отсутствие платной bug-bounty программы.

## Что осталось

- Включить GitHub Private Vulnerability Reporting в настройках публичного
  репозитория; эта настройка не хранится в Git.
- Синхронизировать лицензионные поля DEB/RPM metadata с `SUL-1.0`; RPM builder
  пока использует общее значение `Proprietary`.
- Подготовить `THIRD_PARTY_NOTICES` и включать `LICENSE` и сторонние лицензионные
  уведомления во все бинарные пакеты.
- После первого стабильного релиза заменить pre-release статус в `SECURITY.md`
  точной матрицей поддерживаемых версий.
- Остальные части эксплуатационного и юридического контура из production
  readiness остаются открыты: changelog, SBOM, подписание, provenance и
  формализованная процедура выпуска.

## Риски и решения

- `SECURITY.md` не включает GitHub Private Vulnerability Reporting сам по себе.
  Проверка 2026-08-02 вернула HTTP 404; до включения настройки владельцем
  репозитория ссылка на приватный отчет не образует рабочего канала.
- Целевые сроки ответа не являются обещанием срока исправления. После появления
  поддерживаемых релизов потребуется определить отдельную remediation policy по
  уровням критичности.
- Документ намеренно не обещает юридический safe harbor: такое обязательство
  требует отдельного решения правообладателя и юридической проверки.
