# ALT p11: нужен ли отдельный rollback параметров pam_pwhistory

Рекомендация — сохранить текущую модель (A). Она разделяет настройку
проверки истории, подключение проверки к PAM и сами сохранённые хеши. Менять
её стоит после решения, что именно должно произойти при отключении отдельной
политики, пока проверка истории остаётся подключённой.

## Текущий контракт

* ALT capability из `AltP11Profile.cpp` использует `AltTcbManaged` и отдельный
  `/etc/security/fic-pwhistory.conf`. Её правило передаёт этот путь в `conf=`.
  `pam_pwhistory` читает параметры при вызове. `file=` задаёт отдельное хранилище
  истории, а `remember=0` отключает обработку истории. В поставляемом конфиге
  это начальное значение. См. [документацию Linux-PAM](https://github.com/linux-pam/linux-pam/blob/master/modules/pam_pwhistory/pam_pwhistory.8.xml)
  и [реализацию раннего возврата PAM_IGNORE](https://github.com/linux-pam/linux-pam/blob/master/modules/pam_pwhistory/pam_pwhistory.c).
* `password_history_depth` выставляет `remember`, а
  `password_history_enforce_for_root` управляет флагом `enforce_for_root`.
  На ALT `PamPasswordHistoryOptionPolicy` делегирует в `PamOptionPolicy`.
  `PamConfigFileTransaction` даёт снимок и компенсацию в пределах apply,
  но снимок не переживает аварийное завершение процесса. Успешная запись
  остаётся в файле. ALT не получает managed-entry маршрут для этих
  политик. `effectiveRollbackEnrollment` возвращает `NotEnrolled`.
* Отключение одного параметра останавливает его применение самим FIC.
  Оно не сбрасывает уже записанное значение. Пока подключён
  `pam_pwhistory`, прежняя глубина и правило для root продолжают действовать.
  Это практическая проблема, если администратор ожидает немедленного сброса.
  Отдельное обнуление глубины означало бы изменение работы всей проверки.
* Отключение `enable_password_history` с успешным topology rollback снимает
  блок, который ссылается на этот файл, и восстанавливает правило `pam_tcb`.
  Поэтому сохранённые параметры перестают влиять на этот PAM-маршрут.
  Сторонняя явная ссылка на тот же конфиг может продолжить его читать.
  Если rollback отказал из-за drift, release не считается выполненным.
* Повторная активация может снова использовать оставшиеся значения, в том
  числе ранее заданные параметром, который теперь выключен. Это обратимо
  заданием нужных значений, но может удивить администратора. Конфиг и
  история содержат разное состояние. Очистка конфига не удаляет хеши.
  RPM помечает конфиг `%config(noreplace)`, поэтому обновление сохраняет
  локальные изменения. Снятие topology и судьба файла при erase относятся
  к разным операциям. Этот отчёт не подтверждает native erase.

## Варианты

| Вариант | Что даёт | Риски и сложность | Миграция |
| --- | --- | --- | --- |
| A. Сохранить текущий контракт | Параметры сохраняются между включениями, topology release прекращает их применение по управляемому маршруту. | Отключение параметра не означает сброс. После сбоя операция повторяет проверку и apply, но не восстанавливает прежнее значение по durable снимку. | Не нужна. |
| B. Managed entry для каждого параметра | Точный CAS и durable provenance для каждого значения. Можно восстановить прежний scalar или отсутствие флага. | Нужны семантика baseline, новая маршрутизация ALT, блокировки, доказательство effective значения при дубликатах, компенсация и порядок release при одновременном снятии topology. Ошибка одного параметра может задержать final erase. | Нельзя назначить ownership уже существующим строкам по их содержимому. Для установленных систем нужен явный переход или режим сохранения старых значений. |
| C. Настраивать dedicated файл в рамках ownership всей capability | Позволяет задать один явный контракт для реактивации, например согласовывать параметры с текущим intent перед подключением блока. Не требует независимых записей на каждую строку. | Привязка topology к журналу сама по себе не доказывает владение байтами конфига. Полная перезапись может уничтожить локальные правки. Авария между изменением конфига и PAM targets требует собственной проверяемой границы восстановления. | Ранее изменённые файлы нужно сохранить или явно принять по согласованному контракту. Восстановление заранее неизвестного baseline невозможно. |

Первый шаг при необходимости изменения — описать ожидаемое поведение
отключённых параметров в UI и документации. Если нужен предсказуемый результат
именно при повторной активации, сначала исследовать узкий вариант C:
согласовывать только нужные параметры с текущим intent и проверять их до
подключения блока. Выбирать B имеет смысл при явном требовании независимо
восстанавливать администраторское значение каждого параметра при работающей
capability. Для такого требования нужно отдельно определить поведение
отсутствующего `remember`, поскольку отсутствие строки и `remember=0` могут
иметь разную семантику. Единообразие реализации не оправдывает B.

Исследование основано на текущих ALT profile, policy dispatch, RPM manifest
и upstream Linux-PAM. Production-код для P2 не менялся.
