# Периодическое применение политик

Две числовые политики `GLOBAL/system_settings` читаются один раз при запуске
демона. Сохранение значения, ENABLE/DISABLE, ручной apply и registry reload
не перепланируют работающий процесс и не перезапускают службу. Изменение
действует при следующем запуске FIC, в том числе после перезагрузки компьютера.

| Политика | Диапазон, секунд | ENABLE | DISABLE | Записей нет |
|---|---|---|---|---|
| `check_interval` | 60–86400 | сохранённое значение | 1800 | 1800 |
| `periodic_apply_min_pause` | 0–600 | сохранённое значение; 0 отключает ограничение | 0 | 30 |

Поставляемый GLOBAL.conf содержит обе политики в ENABLE с 1800 и 30.
Явный `--interval` имеет приоритет над `check_interval`. Его прежний parser
сохранён: положительное значение не ограничено диапазоном политики; ошибочное
или неположительное значение даёт 1800. Штатный unit не задаёт `--interval`.
Некорректная включённая настройка без CLI override не заменяется молча дефолтом:
startup отказывает. Невалидная пауза не отменяется параметром `--interval`.

При успешном preflight начало S фиксируется непосредственно перед фактическим
вызовом periodic apply, поэтому длительный preflight не расходует его интервал.
Для предыдущего periodic apply с началом S и завершением F следующий запуск
допустим при `steady_clock::now() >= max(S + I, F + P)`. Завершение включает
обработку результатов и обновление access readiness, даже если проход завершился
ошибкой. При превышении I пропущенные запуски не накапливаются. При P=0 долгий
проход допускает следующий запуск на очередной итерации event loop. Ожидание
паузы не добавляет sleep и не мешает обычной обработке IPC/events.

Отказ существующего preflight переносит основной deadline от времени попытки,
но не записывает завершение несуществующего apply. Первый deadline по-прежнему
считается от начала работы event loop; startup apply не считается предыдущим
periodic apply. Ручные применения и независимые проверки, включая 30-секундную
SSH/incident reconciliation, этими настройками не управляются. Синхронная работа
event loop может фактически задержать любой запуск относительно deadline.

## Существующая конфигурация

Существующий `ConfigSchemaManager` только при package `ensure-config` под
daemon.lock идемпотентно дописывает отсутствующие четыре поля
этих политик. Это целевое additive-обновление схемы 1, без изменения её версии.
Прочие байты, существующие значения и явный DISABLE сохраняются. Частично
присутствующей политике добавляются только отсутствующие поля из дефолтов.
Таким образом GUI/CLI получают действительные сохранённые ENABLE/DISABLE,
числовые значения и диапазоны через обычный PolicyRegistry, без специальных
правил отображения отсутствующей политики.

Обычный startup выполняет read-only `verifyConfigs` и загрузку настроек, не
добавляя ключи и не требуя успешной записи GLOBAL.conf. Старый доверенный конфиг
без этих записей использует I=1800 и P=30. Отсутствие права записи само по себе
этому не мешает; проверки schema/доверенности и отказ на некорректных включённых
настройках сохраняются. Штатные DEB/RPM install/upgrade вызывают `ensure-config`
(или first-install вариант) до complete-install и запуска службы, обеспечивая
появление новых записей для GUI без специальной логики отображения.

Package-обновление требует доверенного GLOBAL.conf и canonical metadata,
использует существующий AtomicFileWriter с identity/content/metadata precondition
и подтверждением durability. Ошибка записи препятствует успешному ensure-config;
она не скрывается. Обычные uninstall и trust-sync маршруты не выполняют обновление.
Политики только валидируют конфигурацию, не владеют ресурсами ОС, не используют
MutationJournal и имеют существующий `NotEnrolled` rollback-контракт GLOBAL.
